**IncidentHub** — backend-сервис для регистрации, назначения и обработки внутренних инцидентов.

Проект разрабатывается как учебное production-oriented приложение на Java и Spring Boot. Основной акцент сделан на управлении жизненным циклом инцидентов, контроле SLA, хранении истории изменений, асинхронной обработке событий и тестировании.

## Статус проекта

Проект находится в активной разработке.

На текущем этапе реализована инфраструктурная основа:

- создан Spring Boot-проект
- настроена Java 21
- подключён PostgreSQL
- добавлен Docker Compose
- подключены Spring Data JPA и Hibernate
- подключены Flyway-миграции
- подключена Jakarta Validation
- добавлен Spring Boot Actuator
- настроены health, liveness и readiness endpoints
- создана начальная модульная структура пакетов

Бизнес-функциональность будет добавляться последовательно по мере разработки.

## Назначение проекта

IncidentHub предназначен для обработки технических и внутренних инцидентов, возникающих в информационных системах компании.

Примеры инцидентов:

- недоступен корпоративный сервис
- не работает интеграция между системами
- недоступна база данных
- превышено допустимое время ответа API
- сотрудник не может войти в учётную запись
- бизнес-процесс заблокирован технической ошибкой
- произошёл сбой при обработке сообщения
- нарушен срок выполнения операции

Система должна позволять зарегистрировать проблему, назначить ответственного исполнителя, отслеживать ход работы и контролировать срок устранения.

## Архитектура

Приложение разрабатывается как модульный монолит.

Каждая бизнес-область выделяется в отдельный пакет и должна содержать собственные модели, сервисы, репозитории и API.

```text
src/main/java/ru/donskikh/incidenthub
├── assignment
├── audit
├── common
├── config
├── identity
├── incident
├── notification
├── sla
└── IncidentHubApplication.java
```

### Назначение пакетов

| Пакет | Ответственность |
|---|---|
| `incident` | Создание инцидентов и управление их жизненным циклом |
| `identity` | Пользователи, роли и аутентификация |
| `assignment` | Назначение и переназначение исполнителей |
| `sla` | SLA-политики, сроки обработки и эскалация |
| `notification` | Системные и пользовательские уведомления |
| `audit` | История изменений и аудит действий |
| `config` | Конфигурация приложения |
| `common` | Общие компоненты и инфраструктурный код |

## Жизненный цикл инцидента

Основной сценарий обработки:

```text
OPEN → ASSIGNED → IN_PROGRESS → RESOLVED → CLOSED
```

Дополнительные переходы:

```text
OPEN → CANCELLED
ASSIGNED → CANCELLED
IN_PROGRESS → CANCELLED
RESOLVED → IN_PROGRESS
```

Переход из `RESOLVED` обратно в `IN_PROGRESS` используется для повторного открытия инцидента, если проблема фактически не была устранена.

### Статусы

| Статус | Описание |
|---|---|
| `OPEN` | Инцидент зарегистрирован |
| `ASSIGNED` | Назначен исполнитель |
| `IN_PROGRESS` | Инцидент находится в работе |
| `RESOLVED` | Исполнитель сообщил об устранении проблемы |
| `CLOSED` | Решение подтверждено, инцидент закрыт |
| `CANCELLED` | Инцидент отменён |

## Приоритеты

В первоначальной модели используются следующие приоритеты:

| Приоритет | Предварительный срок решения |
|---|---:|
| `LOW` | 72 часа |
| `MEDIUM` | 24 часа |
| `HIGH` | 8 часов |
| `CRITICAL` | 2 часа |

На первом этапе значения используются как проектные ориентиры.

В дальнейшем SLA-политики будут храниться в базе данных и настраиваться независимо от кода приложения.

## Требования для запуска

Перед запуском необходимо установить:

- JDK 21
- Docker Desktop
- Git

Отдельно устанавливать Gradle не требуется. В проекте используется Gradle Wrapper.

## Локальный запуск

### 1. Клонирование репозитория

```bash
git clone https://github.com/6yJlka/incident-hub.git
cd incident-hub
```

### 2. Запуск PostgreSQL

```bash
docker compose up -d
```

Локальные параметры подключения:

```text
Host: 127.0.0.1
Port: 5433
Database: incident_hub
Username: incident_user
Password: incident_password
```

На хосте используется порт `5433`, чтобы избежать конфликта с локальным PostgreSQL, который может занимать стандартный порт `5432`.

Внутри Docker-контейнера PostgreSQL продолжает работать на порту `5432`.

### 3. Проверка контейнера

```bash
docker compose ps
```

Контейнер `incident-hub-postgres` должен находиться в состоянии `Up`.

### 4. Запуск приложения

Linux и macOS:

```bash
./gradlew bootRun
```

Windows PowerShell:

```powershell
.\gradlew.bat bootRun
```

После запуска приложение будет доступно по адресу:

```text
http://localhost:8080
```

## Конфигурация приложения

Основная локальная конфигурация находится в файле:

```text
src/main/resources/application.yml
```

Параметры подключения к базе данных можно переопределить через переменные окружения:

| Переменная | Значение по умолчанию |
|---|---|
| `DB_URL` | `jdbc:postgresql://127.0.0.1:5433/incident_hub` |
| `DB_USERNAME` | `incident_user` |
| `DB_PASSWORD` | `incident_password` |

Пример для PowerShell:

```powershell
$env:DB_URL="jdbc:postgresql://127.0.0.1:5433/incident_hub"
$env:DB_USERNAME="incident_user"
$env:DB_PASSWORD="incident_password"

.\gradlew.bat bootRun
```

Реквизиты из `application.yml` и `compose.yaml` предназначены только для локальной разработки.

В production-окружении пароли не должны храниться в репозитории.

## Проверка состояния приложения

Spring Boot Actuator предоставляет endpoint состояния приложения:

```text
GET http://localhost:8080/actuator/health
```

Пример ответа:

```json
{
  "groups": [
    "liveness",
    "readiness"
  ],
  "status": "UP"
}
```

Также доступны отдельные проверки:

```text
GET /actuator/health/liveness
GET /actuator/health/readiness
```

## Миграции базы данных

Для управления схемой базы данных используется Flyway.

Миграции располагаются в каталоге:

```text
src/main/resources/db/migration
```

Файлы миграций должны соответствовать формату:

```text
V1__create_users_and_incidents.sql
V2__create_comments.sql
V3__create_status_history.sql
```

Структура имени:

```text
V<номер>__<описание>.sql
```

Между номером версии и описанием используются два символа подчёркивания.

Hibernate не должен самостоятельно изменять структуру базы данных. Все изменения схемы выполняются через Flyway.
