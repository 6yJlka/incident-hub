# AGENTS.md

Context for AI coding agents working on IncidentHub. Read this file before any task.
Stages, priorities and scope live in `INCIDENT_HUB_PLAN.md`.

## Project

IncidentHub — incident management system built around a service catalog and a service
dependency graph. Modular monolith (deliberate decision, do not split into services).
Backend in the repository root, frontend in `frontend/`.

## Stack (do not change versions without an explicit task)

- Java 21, Gradle (Groovy DSL)
- Spring Boot **4.0.7**. Boot 4 starter names (`spring-boot-starter-webmvc`,
  `spring-boot-starter-flyway`, `spring-boot-starter-*-test`). Never downgrade Boot
  or rename starters Boot 3 style.
- PostgreSQL 16, Flyway, Spring Data JPA
- Spring Security, JWT (JJWT)
- springdoc-openapi **3.0.1**. 3.0.2 and 3.0.3 have a regression (Swagger UI shows
  `null` instead of request examples). Do not upgrade without checking it.
- Tests: JUnit 5, AssertJ, Mockito, Testcontainers (PostgreSQL)
- Frontend: React + Vite + TypeScript, API client generated by Orval from the
  OpenAPI snapshot, react-i18next, nginx in compose
- Docker, Docker Compose, GitHub Actions

## Commands

Backend:

```
./gradlew clean build
```

Integration tests use Testcontainers. Check `docker info` first: without a running
Docker daemon they fail on initialization, and that is not a code problem.
If integration tests fail with schema drift after a migration change, the cause
may be an old local volume. `docker compose down -v` fixes it but deletes all
local data: never run it on your own, report the symptom and ask first.

Frontend (from `frontend/`):

```
npm run api:check
npm run lint
npm run test
npm run build
```

Run frontend checks sequentially, never in parallel: `api:check` regenerates
the client and temporarily removes `src/api/generated`, which breaks tests
running at the same time.

Experiment (separate Gradle source set `experiment`, no Spring, no database):

```
./gradlew generateExperiment
./gradlew runExperiment
```

Outputs go only to `build/experiments/`.

If you redirect command output to log files, write them under `build/`
(for example `build/logs/`), never into the repository root, and do not
leave temporary files behind at the end of a pass.

A task is done only when all of the above pass.

## Workflow

1. One stage — one branch, one PR, squash merge into `main`. Never merge yourself.
2. Work in passes of 1–3 tasks, not the whole stage at once.
3. Before implementing a pass, show the plan of changes by file and key signatures,
   and wait for confirmation.
4. Every commit keeps `./gradlew clean build` green.
5. No new code without tests.
6. Schema changes only through new Flyway migrations.
7. Update README after each stage so it matches reality.
8. At the end of a pass report: what changed, test count, anything left undone
   and why. If something was not found or could not be checked, say so.
9. At the end of a pass that changes backend or frontend code, rebuild and restart
   the local stand so it matches the branch: `docker compose up -d --build`, then
   check `docker compose ps` shows all containers running. Never add `-v` and never
   run `docker compose down -v` (see Commands). If the rebuild fails, report it
   instead of working around it.

## Backend conventions

New code must be indistinguishable from existing code.

### Structure and style

1. Packages by domain, not by layer. Inside a domain: `application/` (use cases),
   `infrastructure/` (Specifications, adapters), `web/` (controllers, DTOs, mapper).
   Entities and repositories in the domain root.
2. One use case — one service class with one public method. Method names: `create`,
   `get`, `assign` and so on; `execute` for lists.
3. Command / Query / Result are Java records validated in the compact constructor.
4. Explicit constructor injection. No Lombok.
5. `Objects.requireNonNull(command, "command must not be null")` as the first line
   of every public service method.
6. Business rules live in entities, not services.
7. Audit is written in the same transaction as the change, with the actor.
8. Do not override `equals` / `hashCode` on entities.
9. Enum fields always explicit `@Enumerated(EnumType.STRING)`.
10. Code, comments and identifiers in English.
11. The application layer does not depend on Spring Security. The current user is
    extracted in the web layer via `@AuthenticationPrincipal AuthenticatedUser`
    and passed into the command as `actorId`.

### Web layer

12. Request and response DTOs are separate records in the domain's `web/`.
13. Required numeric fields in request DTOs are wrappers (`@NotNull @Positive Long`),
    not primitives. Jackson 3 under Boot 4 rejects a missing primitive during body
    parsing, before Bean Validation.
14. List response format: `items, page, size, totalElements, totalPages, hasNext,
    hasPrevious`. Never expose Spring Data `Page`.
15. Status codes: create → 201 with `Location`, delete → 204, lifecycle actions → 200
    with the updated card, reads → 200.
16. Thin controllers, mapping in a separate `XxxWebMapper`.
17. Every `@Operation` has an explicit, unique `operationId` that reads as a client
    function name (`listIncidents`, `createIncident`).
18. Errors are `ProblemDetail` (RFC 9457) with ids `urn:incident-hub:problem:*`.
    New domain exceptions extend `DomainNotFoundException` (→ 404) or
    `DomainConflictException` (→ 409).
19. 403 is neutral: neither the required role nor the `@PreAuthorize` expression
    appears in the response.
20. The user role matrix lives in one place, `IncidentActionAuthorization`. Both
    `@PreAuthorize` (SpEL) and `availableActions` read it. Never duplicate rules.
    Integration authorities (`ALERT_INGEST`) are not user roles and live in
    `security/IntegrationAuthorities`.

### Database

21. Flyway migrations are idempotent and safe for existing data: check data in
    `do $$ ... $$` with a meaningful error, then `update`, then `alter`.
    See V2 and V5.
22. Existing migrations are never edited.
23. `snake_case`, constraint prefixes `chk_`, `fk_`, `uk_`, `idx_`.
24. Unique violations are translated into domain exceptions precisely, by
    `ConstraintViolationException.getConstraintName()`. A bare
    `catch (DataIntegrityViolationException)` is not allowed.
25. No hardcoded ids in data migrations — subqueries by codes.
26. Demo data lives in `db/demo` and runs only under the `demo` profile
    (schema `incident_hub_demo`).
27. No N+1: list endpoints run a fixed number of queries regardless of page content.
    Cover it with a Hibernate statistics test.

### Tests

28. Unit test per service (Mockito) + integration test per repository +
    `@WebMvcTest` per controller. AssertJ for assertions.
29. `@WebMvcTest` explicitly imports `SecurityConfiguration`.
30. The test principal is set via `MockMvcBuilderCustomizer`, not class-level
    `@WithMockUser` (it is wiped under `SessionCreationPolicy.STATELESS`).
31. The default test principal is ADMIN, so a guard test scans controllers and fails
    if a mutating endpoint has no `@PreAuthorize` and is not in the explicit
    exclusion list. Keep it passing; extend the list only with a reason.
32. Every precise constraint translation gets two tests: the race, and passing
    through a foreign constraint name unchanged.

## Frontend conventions

1. The API client is generated by Orval from the OpenAPI snapshot. Never edit
   generated files by hand. After any API change: update the snapshot, regenerate,
   `npm run api:check` must show no diff.
2. All UI text goes through react-i18next keys. Interface language is Russian.
   Codes, statuses and ids from the API (`CORE_DATABASE`, `SEV1`, `IN_PROGRESS`)
   are not translated. Exception: reason codes meant for people (for example
   the `Undetermined` reason of the correlator) are translated through i18n;
   an unknown code is shown as is.
3. Lifecycle buttons come strictly from `availableActions`. The frontend never
   duplicates status transition or role rules.
4. Severity is a numeric colored badge, priority is a plain text label. Two
   independent scales, never mixed.
5. In compose the frontend is served by nginx and proxies the API on the same origin;
   CORS is only for local Vite development.

## Research boundary

The project is also the base for the author's master's research on incident
correlation using the service dependency graph. Infrastructure for it (alerts,
correlator interface, both baselines — time window and the naive PageRank
baseline from the Groot paper — simulator, metrics) is regular work when a task
asks for it. **The graph-based correlation method itself is the research result.
It is designed outside the code; never invent, propose or change its algorithm.
Implement it only from a specification given in an explicit task. If the
specification turns out to be incomplete or contradictory, stop and describe
the problem instead of filling the gap yourself.**

Research documents live in `docs/research/` and are **local only** (the folder is
in `.gitignore`): they become text of unpublished research reports, and publishing
them would trigger plagiarism checks against the author. Read and update them as
asked, never commit them, never quote them in README, commit messages or code
comments. `docs/research/problem-statement.md` is the primary source of
requirements for the method, metrics and experiments; if the plan or the code
contradicts it, it wins — stop and report the contradiction.

The experiment is isolated in the `experiment` source set: product code never
depends on it, it never contains Spring or JPA, and the product jar never
contains its classes. Generation is reproducible by seed; any change of the
algorithm or the order of random draws requires a new `modelVersion`.
