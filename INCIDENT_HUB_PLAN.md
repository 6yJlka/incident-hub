# IncidentHub — план разработки

Документ для передачи ИИ-агенту (Codex): контекст проекта, текущее состояние и
пошаговый план работ с критериями готовности. Стек, команды проверки и конвенции
кодовой базы вынесены в `AGENTS.md` — соблюдать обязательно.

Репозиторий: `https://github.com/6yJlka/incident-hub`

---

## 1. Контекст и цель

IncidentHub — система управления инцидентами, вдохновлённая внутренней SRE-платформой
Т-Банка FineDog (`https://www.tbank.ru/career/technologies/finedog/`).

**Ключевая идея, отличающая проект от обычного тикет-трекера:** центр модели — не заявка,
а **каталог услуг**. Команды регистрируют услуги, между услугами задаются зависимости.
Инцидент привязан к конкретной сломанной услуге, из которой выводится ответственная команда,
а через граф зависимостей можно определить, какие смежные услуги затронуты.

Проект решает две задачи одновременно:

1. Портфолио для трудоустройства на позицию Java Junior/Junior+ backend.
2. Технический задел под НИР в магистратуре: корреляция инцидентов в распределённых
   системах на основе графа зависимостей сервисов. Тема утверждена научным руководителем.

Приоритет — первая задача. Этапы 6–7 обслуживают обе: продуктовая функция приёма
и группировки подозрений и экспериментальная база для НИР — это один и тот же код.

## 2. Текущее состояние

Этапы 1–5 закрыты: каталог и граф, REST и OpenAPI, упаковка и CI, аутентификация
и авторизация, веб-интерфейс.

### Структура

Пакет `ru.donskikh.incidenthub`, модульный монолит. Домены:

- **`incident/`** — сущность `Incident` с инкапсулированным жизненным циклом.
  Переходы проверяются самой сущностью через методы `IncidentStatus.allowsXxx()`,
  нарушение перехода — специализированное исключение. `IncidentAction` — enum
  действий, делегирующий проверку перехода `IncidentStatus`.
- **`catalog/`** — `BusinessService` (услуга с командой-владельцем и уровнем `ServiceTier`),
  `ServiceDependency` (типизированная связь между услугами).
  `GetAffectedServicesService` — обход графа рекурсивным CTE с ограничением
  глубины, защитой от циклов и дедупликацией по минимальной глубине.
- **`team/`** — `Team`, создание и список.
- **`identity/`** — `User` (email, displayName, passwordHash, role, active).
- **`auth/`** — регистрация и вход.
- **`security/`** — `SecurityConfiguration`, `JwtTokenService`,
  `JwtAuthenticationFilter`, `AuthenticatedUser`, `JwtProperties`.
- **`audit/`** — `IncidentAuditEvent` с автором действия, запись в той же транзакции.
- **`common/`** — базовые исключения, `GlobalExceptionHandler` с `ProblemDetail`,
  `OpenApiConfiguration`.
- **`frontend/`** — React + Vite + TypeScript, клиент из OpenAPI через Orval,
  react-i18next, раздача через nginx в compose.

Пустые каталоги `assignment`, `notification`, `sla`, `config` — заготовки, кода нет.

### Перечисления

```
IncidentStatus:   OPEN, ASSIGNED, IN_PROGRESS, RESOLVED, CLOSED, CANCELLED
IncidentPriority: LOW, MEDIUM, HIGH, CRITICAL       // очерёдность работы
IncidentSeverity: SEV1, SEV2, SEV3, SEV4            // влияние на бизнес
IncidentSource:   MANUAL, AUTOMATIC                 // AUTOMATIC пока не используется
IncidentAction:   ASSIGN, START, RESOLVE, CLOSE, REOPEN, CANCEL
ServiceTier:      TIER_1, TIER_2, TIER_3
DependencyType:   SYNC, ASYNC, DATA
UserRole:         REPORTER, ENGINEER, ADMIN
```

### Миграции

```
V1   users, incidents
V2   teams, source, category, responsible_team
V3   incident_audit_events
V4   business_services, service_dependencies
V5   перевод инцидентов с категорий на услуги, severity
V6   удаление неиспользуемых legacy-услуг
V7   демо-данные (только профиль demo, db/demo)
V8   password_hash (nullable) и role пользователя
V9   учётные данные и роли демо-пользователей (db/demo)
V10  actor_id в аудите (nullable для записей до миграции)
V11  backfill авторов демо-аудита (db/demo)
```

Профиль `demo` пишет в схему `incident_hub_demo`, обычный запуск — в `public`.
У схем отдельные истории Flyway, поэтому профили не конфликтуют на одной базе.

Демо-граф: 10 услуг, 10 зависимостей, 4 команды, 6 пользователей, 12 инцидентов.

### Роли и права

| Область | Доступ |
|---|---|
| Регистрация, вход, health, Swagger | публично |
| Создание инцидента | любая аутентифицированная роль |
| Чтение (инциденты, услуги, команды, пользователи) | любая аутентифицированная роль |
| Действия жизненного цикла инцидента | `ENGINEER`, `ADMIN` |
| Каталог услуг, зависимости, команды, пользователи (создание) | `ADMIN` |

### API

Все эндпоинты документированы в Swagger UI на `/swagger-ui.html`, спека на
`/v3/api-docs`, снимок спеки — во `frontend/`. Актуальный перечень — там, а не здесь.

Карточка инцидента возвращает `availableActions` — действия, доступные текущему
пользователю в текущем статусе. Фронт рисует кнопки только по нему.

### Чего нет

- Приёма событий мониторинга и автоматического создания инцидентов — этап 6.
- Симулятора отказов и расчёта метрик корреляции — этап 7.
- Публичного деплоя — отложен, в бэклоге.

### Этап 6. Подозрения и корреляция

**Зачем.** Сейчас инцидент появляется только когда его создаёт человек. В реальной
эксплуатации первичны сигналы мониторинга: один отказ даёт десятки алертов от
зависимых услуг. Этап добавляет приём сигналов, их группировку и превращение
подтверждённой группы в инцидент. Для портфолио это главная SRE-функция проекта,
для НИР — точка, куда подключается исследуемый метод.

**Поток:** алерт приходит на вебхук → коррелятор относит его к группе подозрений
и указывает вероятную корневую услугу → инженер подтверждает группу → создаётся
инцидент с `IncidentSource.AUTOMATIC` на корневой услуге.

**Задачи:**

6.1. **Домен `alert/`.** Сущность `Alert`: внешний ключ события (уникальный),
система-источник, услуга (по коду из каталога), тип сигнала, severity сигнала,
время возникновения и время приёма, краткое описание, ссылка на группу (nullable).
Набор типов сигнала — закрытое перечисление, состав согласовать в плане захода.

6.2. **Вебхук `POST /api/v1/alerts`.**
- Принимает один алерт или пачку.
- **Идемпотентность** по внешнему ключу: повтор не создаёт дубль и возвращает
  уже принятый алерт. Гонку двух одинаковых запросов закрывает уникальное
  ограничение с точечным переводом.
- Аутентификация — **сервисный токен интеграции**, а не пользовательский JWT:
  алерты шлёт система мониторинга, а не человек. Механизм и место в матрице прав
  согласовать в плане захода. Токен с вебхука не даёт доступа ни к чему другому.
- Алерт на неизвестную услугу — поведение согласовать в плане захода.

6.3. **Корреляция.** Интерфейс `AlertCorrelator`: на входе новый алерт и текущие
открытые группы, на выходе решение — в какую группу его отнести или открыть новую,
и вероятная корневая услуга группы. Реализация выбирается конфигурацией.
Первая реализация — **baseline по временному окну**: алерты, пришедшие в пределах
окна, попадают в одну группу; корень — услуга самого раннего алерта. Ширина окна
настраивается.

6.4. **Группы подозрений.** Сущность `AlertGroup`: статус (открыта, подтверждена,
отклонена), вероятная корневая услуга, время первого и последнего алерта,
ссылка на созданный инцидент. Действия:
- **подтвердить** — создаёт инцидент `AUTOMATIC` на корневой услуге (инженер может
  указать другую услугу), алерты группы остаются привязаны к ней;
- **отклонить** — ложное срабатывание.
  Права — `ENGINEER`, `ADMIN`. Аудит действий с автором.

6.5. **UI.** Лента групп подозрений, карточка группы со списком алертов и
вероятным корнем, кнопки подтверждения и отклонения. В карточке инцидента,
созданного из группы, — ссылка на группу.

**Критерии готовности:**
- повторная отправка того же алерта не создаёт дубль;
- вебхук недоступен без токена интеграции, а токен не открывает другие эндпоинты;
- сценарий «пачка алертов → группа → подтверждение → инцидент AUTOMATIC» проходится
  через API и через UI;
- коррелятор заменяется конфигурацией без изменения кода домена.

### Этап 7. Симулятор отказов и стенд оценки

**Зачем.** Экспериментальная база для НИР-2 и НИР-4: воспроизводимые сценарии отказов
на графе зависимостей и метрики качества корреляции. Публичных датасетов по
инцидентам почти нет, поэтому данные генерируются.

**Задачи:**

7.1. **Отделение от продукта.** Код симулятора и стенда — в отдельном пакете
`experiment/`, активен только в профиле `experiment`. Продуктовый код от него
не зависит.

7.2. **Генератор графов.** Помимо демо-графа — синтетические графы заданного размера
и топологии (дерево, слоистый граф, граф с циклами).

7.3. **Генератор сценариев.** Корневой отказ на услуге; распространение на зависящие
от неё услуги по обратным рёбрам с вероятностью и задержкой; шумовые алерты;
одновременные независимые отказы. Всё воспроизводимо по seed.

7.4. **Разметка истины вне домена.** `Alert` ничего не знает об эксперименте.
Симулятор генерирует внешние ключи событий и сам хранит сопоставление
«ключ → сценарий, корневая услуга». Коррелятор не имеет доступа к разметке.

7.5. **Прогон и метрики.** Поток алертов прогоняется через выбранный `AlertCorrelator`
(напрямую, без HTTP, для скорости; сквозной прогон через вебхук — опционально).
Метрики:
- precision, recall, F1 группировки (попарно по алертам);
- точность указания корневой услуги;
- сокращение шума — во сколько раз групп меньше, чем алертов;
- доля ложных подавлений — независимые отказы, ошибочно слитые в одну группу.

Результат — CSV или JSON с параметрами прогона и seed.

**Критерии готовности:**
- один и тот же seed даёт один и тот же поток алертов и те же метрики;
- baseline по временному окну прогоняется на нескольких графах и уровнях шума;
- продуктовая сборка без профиля `experiment` не содержит его бинов.

### Бэклог

Порядок — по убыванию ценности.

- **Деплой на публичный хостинг.** Образ, compose и CI готовы с этапа 3; деплой —
  подключение образа к платформе и ссылка в README. Отложен.
- **Хроника инцидента.** `IncidentUpdate`: текстовые обновления, автор, время.
  Поле «место обсуждения» (ссылка на чат).
- **Оптимистическая блокировка** `@Version` в `Incident`: сценарий «карточка открыта
  у двоих» появился вместе с UI.
- **Подписки и эскалации.** Подписки на услуги; политика эскалации по времени
  и критичности; уведомления через Kafka с паттерном **Transactional Outbox**;
  шедулер эскалаций.
- **SLA.** Срок устранения по критичности, дедлайн в карточке, признак нарушения.
  Не путать с SLO — SLO относится к детектированию.
- **Постмортемы.** Корневая причина, таймлайн, follow-up задачи с ответственными.
- **Аналитика.** MTTR, MTTD, доля инцидентов с выявленной причиной,
  распределение по услугам и командам.
- **Суммаризатор хроники** через внешний LLM-API.

## 4. Чего делать не нужно

- **Не реализовывать и не предлагать графовый метод корреляции** — это научный
  результат НИР-2. Интерфейс коррелятора, baseline, симулятор и метрики делать
  можно, когда они в задании.
- Не подключать реальный мониторинг (Prometheus, Grafana). Достаточно вебхука.
- Не добавлять Lombok, не менять стиль на «толстые» сервисы, не понижать Spring Boot,
  не обновлять springdoc выше 3.0.1 без проверки регрессии с примерами.
- Не реализовывать AI-модули, релизы и GitOps-конфигурацию из FineDog.
- Не делать микросервисы. Модульный монолит — осознанное решение.
- Не дублировать во фронте правила переходов статусов и ролей.
